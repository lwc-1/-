# 面试讲解参考

## 1. 为什么选办公文档场景？

**回答要点：**

> 选择办公文档场景有两个原因。第一，办公文档是 AI 办公产品（如 WPS AI、文档助手、PDF 工具）的核心应用场景，和实际业务高度相关。第二，文档处理类任务有明确的参考答案和可量化的评测标准，比如 JSON 格式是否可解析、关键信息是否完整抽取，这样评测结果更加客观可靠。

---

## 2. 测试用例怎么设计的？

**回答要点：**

> 我的用例设计遵循三个原则：
>
> 1. **场景真实性**：所有用例都来自真实办公场景，比如会议纪要、项目周报、合同信息抽取等，不是随便编的抽象问题。
> 2. **分层覆盖**：采用 L1-L3 分层框架，L1 是"办公文档处理能力"，L2 分为信息抽取、文档摘要、格式转换、多轮上下文四类，L3 再细分成 12 个子领域，保证评测覆盖面。
> 3. **可评判性**：每条用例都定义了 reference_points（参考要点）、expected_format（期望格式）和 constraints（约束条件），这样机评和人评都有明确标准。

---

## 3. 评测维度怎么设计的？

**回答要点：**

> 我设计了 5 个评测维度：
>
> - **指令完成度**：模型有没有做完用户要求的事情
> - **内容准确性**：有没有出现幻觉或事实错误
> - **格式正确性**：输出的 JSON/表格等格式能不能用
> - **完整性**：有没有遗漏关键信息
> - **上下文一致性**：多轮对话中有没有丢失前面的信息
>
> 每个维度都有 1-5 分的量化标准。这 5 个维度是参考了业界主流 AI 评测方法（如 Chatbot Arena、MT-Bench）并结合办公文档场景特点设计的。

---

## 4. 机评脚本怎么实现的？

**回答要点：**

> 机评采用了 **LLM-as-Judge + 规则校验** 的双层方案：
>
> 1. **规则校验层**：用代码直接检查客观指标，比如 JSON 能否解析、关键词是否出现、字数是否超限。这层不依赖模型判断，结果确定性高。
> 2. **LLM-as-Judge 层**：把测试用例、模型回答、评分标准一起输入给 Judge 模型，由它按 5 个维度打分。相比纯人工评分效率高得多。
>
> 技术实现上，我用的 Python + OpenAI SDK，因为 OpenAI SDK 支持 base_url 配置，所以 DeepSeek、GPT、硅基流动等任何兼容 API 都可以即插即用。还加了 tenacity 做重试机制，防止偶发网络错误导致整个评测中断。

---

## 5. LLM-as-Judge 不稳定怎么办？

**回答要点：**

> 这是个好问题。LLM-as-Judge 确实存在评分不稳定的情况，我做了几个措施来应对：
>
> 1. **Judge 温度设低**：Judge 模型的 temperature 设为 0.1，降低随机性。
> 2. **强制 JSON 输出**：要求 Judge 严格输出 JSON 格式评分，避免模棱两可的自然语言表述。
> 3. **规则校验兜底**：格式类指标不完全依赖 Judge 判断，代码直接校验。
> 4. **人工抽检对照**：抽取 30% 用例做人评，计算机评-人评一致率，如果一致率低说明 Judge prompt 需要优化。
> 5. **评分偏差分析**：分析偏差集中在哪个维度或哪个 L2 领域，针对性优化评分标准描述。

---

## 6. 人评抽检怎么做的？

**回答要点：**

> 我写了一个脚本自动从结果中随机抽取 30% 的用例，生成一个 CSV 表格模板。模板里包含模型回答和机评分数，同时留出人评打分列。我自己按同样的评分标准对这些用例打分，然后对比机评和人评的差异。
>
> 如果差异大，我会分析原因：
> - 是评分标准写得不够清晰导致 Judge 理解有误？
> - 是某个维度定义太模糊？
> - 还是 Judge 模型本身能力不足？
>
> 根据分析结果优化 Judge Prompt 或评分标准，这是一个迭代优化的过程。

---

## 7. Bad Case 怎么分析的？

**回答要点：**

> Bad Case 分析分三步：
>
> 1. **识别**：综合分 < 4.0 的用例自动标记为 Bad Case
> 2. **归因**：给每个 Bad Case 打标签，比如"格式不符"、"信息遗漏"、"幻觉"、"上下文丢失"。然后统计各标签出现频次，看哪类问题最集中。
> 3. **归纳**：按 L2 维度分析，如果"格式转换"类通过率明显低于其他类，说明模型在格式遵循能力上有短板。
>
> 最后输出优化建议，比如：在 system prompt 中加格式约束、用 few-shot 示例引导、或者对低分领域扩充测试用例做回归测试。

## 8. 如果接入真实 PDF Skill 要怎么扩展？

**回答要点：**

> 现有框架设计上是松耦合的，接入真实产品主要改两个地方：
>
> 1. **输入层**：现在用例是纯文本，如果接入 PDF Skill，需要增加文件上传模块，把 PDF 文件作为输入的一部分传给模型。
> 2. **输出解析层**：如果模型返回的是文件（比如生成了一个 PDF），需要增加文件下载和内容提取模块来判断效果。
>
> 但评测框架本身（L1-L3 分层、5 维度评分、报告生成、Bad Case 分析）是完全可以复用的，不需要重新设计。

---

## 9. 如果要开发 Agent，下一步怎么做？

**回答要点：**

> 基于现有项目，下一步可以做一个「评测全流程自动化 Agent」。Agent 的输入是产品文档或需求描述，它能自动完成：
>
> 1. 根据产品文档生成测试用例集
> 2. 确定评测维度和评分标准
> 3. 调用 API 执行评测
> 4. 分析结果并生成报告
>
> 核心思路是把现有项目中人工操作的部分（用例设计、维度选择）也交给 LLM 来做，用 Chain of Thought 或 ReAct 模式串联各个步骤。Agent 框架可以用 LangChain 或者自己用 function calling 实现。

## 通用面试小贴士

1. **说具体数字**：用例数量、维度数量、通过率都要说具体的
2. **说遇到的问题**：比如 Judge 不稳定、JSON 解析失败，说你怎么解决的
3. **说设计思考**：为什么选这 5 个维度而不是 3 个？为什么要分 L1-L3？
4. **不要背**：用自己的话讲，面试官听得出来
5. **准备跑一遍**：面试前真实跑一遍完整流程，用实际数据说话

## 10. 多模型对比是怎么做的？

**回答要点：**

> 我对 DeepSeek-V4（大模型）和 Qwen2.5-7B（小模型）进行了横向对比评测。用同一套 48 条测试用例分别跑两个模型，然后对比各维度得分。
>
> 结论是 DeepSeek 平均分 4.89，通过率 96.7%；Qwen-7B 平均分大约 3.6-3.8，通过率约 65%。差异主要体现在：
>
> 1. **格式遵循**：小模型经常无视"输出纯JSON"的约束，自作主张加代码块或解释文字
> 2. **复杂指令跟踪**：多轮对话中，小模型容易丢失前面轮次的修改要求
> 3. **数字精度**：小模型在金额、百分比等数字提取上更容易出错
> 4. **幻觉问题**：信息不完整时，小模型更倾向编造数据，大模型更老实
>
> 这个对比说明了一个重要结论：模型规模对办公文档处理任务的影响主要不在"能不能做"，而在"做得精不精准"。

## 11. 为什么选 DeepSeek 和 Qwen 对比？

**回答要点：**

> 选择这两个有三个原因：
>
> 1. **业务相关**：DeepSeek 和 Qwen 都是国产模型，金山的业务场景大概率也是对接国产模型
> 2. **规模差异**：DeepSeek-V4 是大参数模型，Qwen-7B 是小模型，对比有区分度
> 3. **成本考量**：实际业务中不可能所有场景都用最贵的大模型，需要评估小模型在哪些场景"够用"，可以降低成本

## 12. 48 条用例够不够？实际工作中用例量是多少？

**回答要点：**

> 48 条用于 demo 和验证链路是够的。实际工作中，一个成熟的评测集通常有 200-500 条以上，覆盖更多边界条件和线上真实 case。
>
> 但核心不是数量，而是**覆盖度和区分度**。我在设计用例时有两个原则：
> 1. 覆盖度：确保每个 L2/L3 领域都有用例覆盖
> 2. 区分度：后来发现常规用例模型基本都满分，所以补充了 18 条"刁钻"用例（格式强约束、幻觉诱导、矛盾检测等），才把不同模型的能力差异显现出来
>
> 如果入职后做真实评测，我会基于线上用户的真实 query 来扩充用例集。
